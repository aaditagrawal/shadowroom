# Catalog, indexing, and grouping

`Catalog::open(&Path)` creates a local SQLite catalog in WAL mode with FULL synchronous commits. The application must pass its internal application-data directory, never a source drive. The indexer rejects a catalog underneath the selected source root. Clones share a mutex-protected connection; metadata work occurs outside that lock and writes use transactions of 64 records by default. User ratings, pick/reject flags, and labels survive reindexing. `set_decisions(&[PhotoDecision])` applies an entire selection atomically for background persistence and undo. `flush()` runs a FULL WAL checkpoint after queued transactions have committed; decision durability does not depend on waiting for a checkpoint. The indexer records imported source roots; exports reject destinations inside them.

Start an import with `Indexer::start(catalog.clone(), root, IndexOptions::default())`. `root` can be a whole mounted drive or any selected folder. `IndexOptions` contains `pair_raw_jpeg`, `read_exif`, and `batch_size`. The returned `IndexJob` owns a background thread, exposes `events: Receiver<IndexEvent>`, and supplies `cancel`, `is_finished`, `try_recv`, `recv_timeout`, and consuming `join`. Dropping the job requests cancellation without blocking the UI. Retain the job while importing.

Events are `Started(PathBuf)`, `Progress(IndexProgress)`, `Error { path, message }`, `Finished(IndexProgress)`, and `Cancelled(IndexProgress)`. Progress has `scanned`, `indexed`, `unchanged`, `errors`, `current_path`, and `elapsed_ms`. A fatal setup/database failure emits `Error` and ends the job. `is_finished` also covers these failures. At most the first 100 per-file errors are emitted; the progress count includes every error. A cancelled scan commits already read records and retains existing records and decisions. It never interprets an unplugged or temporarily unavailable drive as deleted photos.

Indexing enumerates each directory once and traverses regular files only, skips hidden and common system directories, and never follows symlinks. It buffers one directory for pairing, never decodes pixel buffers, and compares file size, millisecond modification time, and extraction revision before reading metadata again. Revisions refresh previously extracted metadata once without changing decisions. Incremental fingerprints are read using the indexed source-path range and a small SQL projection; the scan does not deserialize the entire catalog into Photo records. JPEG and RAW files with a case-insensitive matching stem in the same folder become one photo, with RAW as the original and `companion_path` as its preferred preview. Both files are copied for a pick. Companion size/mtime participate in incremental detection. When a previously indexed JPEG acquires a RAW, its decisions move to the paired record. Recognized files with metadata errors retain a catalog entry with available filesystem metadata. HEIC/HEIF/HIF/AVIF files are indexed even when a decoder is unavailable. RAW pairing prefers JPEG, then HEIF; codec availability affects previews, not catalog admission. HEIF previews use the existing dynamically loaded libheif path and show an unavailable-codec diagnostic when necessary.

Metadata includes EXIF capture timestamps, subsecond precision, explicit UTC offsets when present, camera/lens, exposure, dimensions, and orientation. **Original RAW metadata is read first** from a bounded header; paired JPEG metadata only fills missing fields. A reduced, processed, or edited JPEG cannot replace known RAW dimensions, camera, lens, exposure, orientation, or capture timestamp. Classic TIFF RAW SubIFDs marked CFA/LinearRaw are inspected in that same prefix to find source dimensions when IFD0 contains only a reduced preview. The scan is bounded to 64 IFDs, 512 entries per IFD, and 32 SubIFD links per entry. No pixel data is decoded or reread for this step. A JPEG is not inspected when the RAW already contains all displayed metadata.

`Photo.captured_offset` preserves the original `OffsetTimeOriginal` string; `capture_time_kind` is `offset` for known offsets and `camera_local` otherwise. Known-offset capture times are normalized to UTC milliseconds in `captured_at`, and `Photo::capture_display()` restores the original camera wall time plus its explicit offset. Offsetless EXIF datetimes use a neutral wall-time timeline so ordering within the camera does not depend on the indexing computer's timezone; they display `(camera local)` rather than a false UTC suffix. A paired JPEG's known offset can fill a missing RAW offset while retaining the RAW clock and subseconds. Malformed offsets remain unknown. Legacy rows without provenance display `(offset unavailable)` until the next index pass refreshes them. Missing or invalid capture times display `—`.

TIFF-based RAW extraction reads a maximum 256 KiB header prefix and retains valid partial EXIF fields; it does not use the EXIF library convenience method that reads an entire RAW. Metadata outside that prefix may be unavailable. If RAW dimensions are unavailable, only then can JPEG dimensions supply a fallback; these cannot establish unseen sensor dimensions. JPEG/PNG/HEIF/WebP EXIF extraction caps actual reads at 2 MiB while allowing seeks. No source file is opened for writing.

`discover_drives()` enumerates mounted Linux block devices at `/media`, `/run/media`, and `/mnt`, plus USB/removable block devices mounted elsewhere using sysfs; macOS uses `/Volumes`. Each `Drive` supplies `name`, `path`, `removable`, and `photo_folders` (existing DCIM, Pictures, Photos, PRIVATE/MP_ROOT variants). These folders are suggestions; importing `Drive.path` always walks the entire drive. Discovery reads native mount information without invoking platform shell commands.

`group_photos(&[Photo], GroupingOptions)` returns all photo IDs, including singleton groups, in input order. Options are `mode`, `gap_ms`, `hamming_distance`, and `max_neighbors`. Modes are `Off`, `Time`, `Visual`, and `Burst`. Images are partitioned by folder/camera and sorted by EXIF time (mtime fallback). Time mode links adjacent images within the gap. Visual mode requires known dHashes within the temporal window; Burst starts with time and adds visual evidence as hashes become available.

Visual and Burst groups keep a known representative. Incoming frames must agree with both a nearby frame and that representative when hashes exist. Each incoming frame joins one existing group, preventing an unknown preview from bridging incompatible known scenes and reducing gradual similarity drift. Burst groups additionally cap total span at eight capture gaps (clamped to 2–30 seconds) and 256 frames; Time mode retains unrestricted temporal chaining for deliberately broader event groups. These are heuristics, not subject recognition or a sharpness/blink model. Crop changes, flat images and missing metadata can still produce imperfect suggestions.

Visible and selected previews are analyzed first. Enabling Visual or Burst also starts a bounded low-priority thumbnail analysis, at most two pending images, while interactive preview work stays ahead. This can read an uncached source; it reuses paired JPEGs/embedded previews and the persistent local thumbnail cache. Hash writes are batched. Comparison count is bounded by 256 neighbors per image (default 32): O(n log n + n k), rather than whole-catalog pairwise comparisons.

`prepare_export(destination, picks, ids)` snapshots decisions into an owned `ExportPlan`; `execute()` performs validation and file I/O on a dedicated worker. The compatibility methods `export_xmp` and `export_picks` also delegate to plans. Only the selected export inputs are validated and parent folders are deduplicated; unrelated offline photos do not block export. `export_xmp(&ids, destination)` creates Adobe-compatible XMP rating/color fields plus a Shadowroom pick/reject field. Rejects use XMP rating -1. A collision-safe JSON manifest maps each source path to its actual sidecar filename so duplicate basenames remain identifiable. `export_picks(destination)` copies picked originals and paired JPEGs. Exports create destination files atomically with `create_new` and add numeric suffixes for collisions; existing files are never overwritten. Read/copy/write errors are returned and a failed partial output is removed. Decisions, hashes, and caches remain internal unless the user explicitly exports them.

## Ingest schema and transactions

See [INGEST.md](INGEST.md) for the import workflow and safety model. Index-in-place remains available through `Indexer` and the legacy `import` MCP tool; the desktop folder/drive action now opens the copy Import pane.

`Catalog::open` performs an additive, idempotent SQLite migration without rewriting existing photo metadata or decisions:

- `ingest_log`: `id`, `source_volume`, `source_relative`, `original_filename`, `size`, `mtime_ns`, `capture_ms`, `capture_kind`, nullable `content_hash`, JSON `destinations`, JSON `backups`, `job_id`, `imported_at`, and JSON `data` containing complete group/file output records. Indexed by known hash, filename/size/capture, and filename/size/mtime. Mtime is nanoseconds here; ordinary Photo/indexer mtimes remain milliseconds.
- `ingest_jobs`: `id`, `started`, nullable `finished`, `source`, JSON `options`, JSON `counts` (complete progress summary), `bytes`, JSON `errors`, and `verification` phase. Interrupted jobs retain their running state for diagnosis.
- `ingest_sequences`: primary key `key`, nonnegative `value`. Keys are `stored` and `day:YYYY-MM-DD`; no counters are reserved during planning. The day key applies the configurable day-start hour to camera wall time.

After every group verifies on all destinations, a single transaction inserts its log row, inserts destination photo rows with cull decisions and advances applicable counters. Destination photo IDs are new catalog identities; source IDs and decisions remain intact. An identical existing output is recorded without replacing it or advancing a counter. Explicit mark-as-imported records no copy and advances no counter. Failure before the transaction commits rolls back only this job's filesystem entries. One catalog-level ingest lease serializes copy jobs sharing a Catalog; ordinary decision writes continue using the shared connection between short transactions. Ingest workers index completed destination folders with the existing indexer after copy; video records remain history-only.

Seen checks are independent of mount prefix: known BLAKE3 → exact original filename/size/capture → filename/size/mtime within ±24 hours in exact 15-minute steps. A known hash mismatch blocks weaker matching. Both EXIF provenance and mtime fallback are retained so mtime fallback does not masquerade as an exact EXIF capture match.
